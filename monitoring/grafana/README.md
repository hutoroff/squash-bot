# External Grafana templates (not provisioned)

These files are repository-local templates for an **existing external Grafana OSS instance**, not an application Compose service or permission to modify Grafana. The current Grafana version, organization/folder permissions and provisioner are **not known** from this repository. Shapes follow the [Grafana 10.4 file-provisioning format](https://grafana.com/docs/grafana/v10.4/alerting/set-up/provision-alerting-resources/file-provisioning/) (Grafana-managed multi-dimensional rules and JSON equivalents of the documented YAML examples). The pinned Prometheus 3.9.1 image checks every alert's PromQL offline. Actual import/export round-trips against the owner's Grafana version, contact tests, firewall and data-source connectivity are **Step 14 owner-authorized gates**, not accomplished by these checks. Do not apply incompatible templates speculatively.

## Safe query connectivity and secret boundaries

- Grafana must query Prometheus **server-side** (`access: proxy`), through a private address/VPN path to the application host's query port. Compose binds that port to host `127.0.0.1` by default: a remote VPN route needs an explicitly approved private binding, firewall and verification from outside. Do not use Docker DNS `prometheus` from the separate Grafana host. Alternatively, leave the origin bound to loopback and use an HTTPS reverse proxy on the application host that connects to `127.0.0.1:9090`, requires **separate query authentication**, and restricts sources to Grafana's address(es). Test both an authorized Grafana query and an unauthorized external attempt before use. Never expose `:9090` directly to the internet or proxy the application admin/registry ports; do not enable Prometheus lifecycle, admin or remote-write receiver endpoints. Beware Docker-published-port/firewall bypass behavior: external reachability needs its own operational test.
- Select **one** `datasource-*.example.yaml` for file provisioning in Grafana's `provisioning/datasources/`. The `.yaml` files contain JSON (valid YAML flow syntax) so offline checks can parse them without a YAML dependency. Both use `SQUASH_PROMETHEUS_URL` as a Grafana-side environment placeholder for a reachable private or HTTPS URL, never a browser URL. The proxy example also references `SQUASH_GRAFANA_QUERY_TOKEN` in `secureJsonData`; this token belongs only to the authenticated query proxy. It must **not** be the application's `MONITORING_TOKEN`, `INTERNAL_API_SECRET`, or either Telegram bot token. Keep it in Grafana's secret store/env, not in a tracked file or shell history. With a private/VPN source and no proxy authentication use the private example, still restricting network access.
- The Grafana Telegram receiver is only an **example**; use a separate monitoring bot and a monitoring chat, passed securely as `SQUASH_MONITORING_TELEGRAM_TOKEN` and `SQUASH_MONITORING_TELEGRAM_CHAT_ID` to the external Grafana provisioning environment, never from the app's `.env`. The receiver sends resolved notifications (`disableResolveMessage: false`). Confirm bot and chat routing only in an authorized notification test. This alerting path does not rely on application Telegram or management. If an existing contact has the same UID/name, merge or rename rather than overwriting it.

## Rules, dashboard, policies

- `dashboard.json` is a provisionable dashboard model. `dashboard-provider.example.yaml` supplies an example file provider pointing at a Grafana-local dashboard directory; adapt path/org/folder to the existing instance. `alerts.json` contains one Grafana-managed rule group (`30s` evaluation) with fixed deployment `squash-bot`, bounded service grouping, explicit `noDataState` and `execErrState`. Static management/monitoring and health rules fail alerting on No Data/Error. Inventory missing/duplicate rules use NoData when management storage is down instead of misreporting a service as missing; Grafana may generate `DatasourceNoData`, so route that synthetic alert to the monitoring contact. The **optional** provider-ledger rule is initially paused and uses NoData: only enable it when booking is in the required inventory. Query failures alert rather than presenting recovery. Verify provisioning order: create the folder and datasource UID before importing dashboard/rules.
- The management `up{job="management"}` series is static, independent of HTTP SD. Inventory from management produces zero eligible counts for a service that never registered or expired; a storage outage removes the derived missing-service series (the rule transitions to NoData rather than a false missing-service condition), not the separate storage-health alert. `squash_service_ready` identifies a scraped but locally unready instance. The scheduler uses the final sequential job's **returned** timestamp and a process-start fallback before its first completion. Prometheus preserves the scrape's `job="management"` and renames the application's per-scheduler-job label to `exported_job` (default `honor_labels: false`); dashboard/rule queries account for this. No rule infers business success from `unclassified` scheduler runs.
- A new `booking_external_executions_total{outcome="unknown"}` event alerts immediately (`for: 0s`); two separate durable gauges (`booking_operations_unknown` and `squash_management_booking_operations{state="outcome_unknown"}`) keep existing liability visible after restarts/counter resets. The provider ledger metrics currently return zero if the ledger read fails; a missing required booking instance/readiness alert is the fallback, **not** proof that zero means no unknown operations. Validate the booking key is in `MONITORED_SERVICE_KEYS`/auto-added binding. Alert thresholds and polling intervals are starting values, not a tested production SLO.
- **Never apply `policy.example.json` directly to a populated organization.** Grafana file-provisions the **entire notification policy tree** and would overwrite unrelated policies. Merge the example child route into an owner-reviewed exported tree. Group by `deployment`, `service_key`, `alertname`; initial wait 30s, group interval 5m, repeat 1h. Ensure Grafana-generated `DatasourceError`/`DatasourceNoData` alerts also reach a monitoring contact (not merely a label-matched route if synthetic alerts lack `deployment`); root fallback must be safe. `mute-time.example.json` only defines a sample Sunday UTC interval; it is **not attached** to the policy. Attach an owner-approved maintenance mute to the specific child route only for a real planned window, and verify recovery messages resume. Do not mute foundational monitoring failures indefinitely. Keep `scripts/healthcheck.sh` until end-to-end alert delivery is proven, then plan overlap removal separately.
- All alert rule labels are bounded; no user/game/account/operation IDs, credentials, or raw paths are dashboard variables or alert labels. The owner must confirm `deployment: squash-bot`, current Grafana version, accessible URL, disk/retention budget and independent notification contact before rollout.

## Offline verification

```sh
node monitoring/grafana/generate.mjs --check
node scripts/checks/grafana-config-check.mjs
```

The check compares generated JSON with `generate.mjs`, validates structural invariants and runs `promtool check rules` plus `promtool test rules` against **synthetic**, disposable mirror rules from `alert-fixtures.yml` in a network-disabled container. Fixtures cover missing/failed static management, never-registered and expired targets, registry failure, unsupported duplicates, unready services, stalled/healthy polls, monitoring loss, and recent versus durable booking unknown outcomes. Prometheus alert rules in the temporary fixture are **not** deployed as notification rules. This verifies PromQL semantics (including zero/no-series conditions), not Grafana's rule evaluation/provisioning schema or real alert delivery. Grafana folder permissions, query endpoint and notification integration need separate owner-authorized checks.
