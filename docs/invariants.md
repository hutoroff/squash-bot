This is a navigation map for risky changes, not a claim of complete coverage. **Covered** means a specific focused check exists; **partial** means nearby tests cover only some of the stated behavior; **gap** means no adequate end-to-end check was identified. Inspect the test assertions and current code before relying on any row.

## How to use this map

- When a change touches an invariant, read both implementation and relevant test assertions; extend tests for the changed failure modes.
- When fixing a bug, establish that the regression test would fail against the broken behavior where practical.
- Update the row when a gap is genuinely closed, not just because a suite is green or a mock asserts the implementation's new behavior.
- Treat ambiguous booking outcomes and authorization changes as explicit design decisions; do not silently invent safe retry or trust assumptions.
- The [development guide](development.md) documents current commands and false-success integration-skip limitations. Test state and coverage observations can become stale; re-run relevant checks for the current task.
