# Discovery and monitoring rollout handoff (not a deployment authorization)

This is an **unexecuted operator checklist and evidence template** for a single-active deployment. Repository-local tests and templates are tracked in the [acceptance matrix](service-discovery-acceptance-matrix.md). Do not use a green `make check` as permission to enable production booking mutations, switch callers, provision Grafana, send a notification, or run a live drill. Those actions are [Step 14](service-discovery-implementation-plan.md) and require separate owner authorization. Never run a second Telegram process merely to inspect it: polling can delete the existing webhook. Do not scale management's cron or booking's executor.

## 1. Preflight and independent gates

- Identify the **exact candidate revisions** of all four services and monitoring templates, the production network/interface/subnet, logical keys, booking facility/sport binding and migration compatibility. Do not publish incompatible `:stable` tags independently through Watchtower. Validate the shared external bridge's actual address against management's `DISCOVERY_ALLOWED_CIDRS`; perform any network migration in an approved stop-before-start window. Production Compose uses an operator-created external `squash_services` bridge, not a private-isolation guarantee; the web ingress and Prometheus loopback query port are the only intended published ports. See [Prometheus setup](../monitoring/prometheus/README.md) and the [Compose topology](../docker-compose.prod.yml).
- Provision separate protected `INTERNAL_API_SECRET` (service/registry business bearer), `MONITORING_TOKEN` (admin/HTTP SD/scrape bearer), web/management `JWT_SECRET`, and booking `BOOKING_IDENTITY_KEY`; keep Grafana's query-proxy token and independent notification bot **outside** the application `.env`. Use an existing private absolute host token file readable by the pinned Prometheus UID, and confirm TSDB retention/disk headroom; never put bearer values in committed YAML, commands or evidence. See the [monitoring](../monitoring/prometheus/README.md) and [Grafana](../monitoring/grafana/README.md) guides.
- Keep `DISCOVERY_MODE=static` and configured static business URLs while testing registration. `DISCOVERY_URL` is only an optional shadow registration/bootstrap address in this phase, not a routing switch. Keep management, Telegram and booking **one active process each**. Booking's PostgreSQL singleton protects booking execution, not management's scheduler, Telegram wizards, or manual provider activity; do not overlap old and new booking executors during replacement.
- Before **any** production booking mutation activation, independently satisfy the [booking reliability hard gates](booking-reliability-runbook.md#1-hard-gates): pause mutations, inventory active legacy provider bookings, import only verified exact matches, preserve ambiguous liability, create a fresh **whole-database** backup covering both migration streams, and test a disposable restore with the protected matching booking identity key. `BOOKING_RELIABLE_CUTOVER_ACK=keyed-v2-only` is only a compatibility acknowledgement, not proof of these gates. Unsafe keyless/v1 rollback keeps mutations paused. Discovery routing does not remove these obligations.
- Record `make check-fast`, `make check`, `make check-secrets`, `make check-security` results separately. A scanner finding or network/tool error is a failure, not a pass. The [security triage](security-checks.md) records existing dependency debt; an owner decides its release disposition. Offline [Prometheus](../monitoring/prometheus/README.md#synthetic-checks-no-application-startup) and [Grafana](../monitoring/grafana/README.md#offline-verification) checks validate templates, not the installed monitoring stack.

## 2. Shadow registration and monitoring, static routing unchanged

1. In an authorized maintenance window, set `DISCOVERY_URL` while retaining `DISCOVERY_MODE=static` and the **existing static business URLs**. Start management/DB first; separately start the single booking, web and Telegram instances. The management-local registrar and other registrars retry when the registry is absent; booking can serve direct keyed v2 traffic without management if its own DB/singleton is healthy. Observe protected local readiness separately from dependency availability; missing booking does not make management unready.
2. Compare each authenticated admin descriptor to the immutable management catalog: logical `service_key`, kind, contract major/capabilities, exact booking facility scope, instance ID, advertised private admin/API host and port. Observe ready heartbeats and lease renewal through an expiry interval; compare expected singleton counts to *eligible ready* counts. A starting, draining, expired or ambiguous membership is not a usable booking endpoint. An unready instance can still be scraped while its registration is non-terminal. A registry database outage is **unavailable**, not a known-empty catalog or evidence that the provider has no bookings.
3. Confirm Prometheus's **static management scrape** and authenticated HTTP SD for other instances from the actual private bridge, including Telegram in the selected polling **or** webhook transport. Check targets appear on registration and disappear after drain/lease expiry; confirm no duplicate management scrape, required-service zero/count rules (including never-registered targets), local readiness, scheduler timestamps, unresolved booking/notification gauges and bounded labels. Prometheus only binds its query port to host loopback by default. No customer IDs, operation IDs, account logins, raw paths or secrets may appear in labels. Keep registration separate from routing throughout this phase.
4. The external Grafana instance/version, private query route or separately authenticated allowlisted HTTPS proxy, provisioner/folder/datasource, No Data/Error behavior, independent monitoring contact, and test notification all need **owner validation**. The repository templates are not installed. Test that public ingress and unauthorized sources cannot reach admin/registry/scrape/query endpoints; Docker port publication may bypass host firewall assumptions. Keep `scripts/healthcheck.sh` active until the external alert path, recovery messages and Prometheus/whole-host loss behavior are observed end to end.

## 3. One caller class at a time (only after preflight and shadow evidence)

- For **web**, set its `DISCOVERY_MODE=registry`, `MANAGEMENT_SERVICE_KEY` to the reviewed management binding, `DISCOVERY_URL` to the bootstrap endpoint, and `MANAGEMENT_SERVICE_URL=` empty. Verify signed sessions survive management target replacement/outage, while protected business calls fail closed on missing, ambiguous, incompatible or unavailable registry resolution. Do not change owner authorization rules or expose the management business listener publicly.
- For **Telegram**, perform a stop-before-start replacement of the one bot. Set its registry mode/key/bootstrap and clear `MANAGEMENT_SERVICE_URL`. Verify management contract compatibility before update consumption, authenticated webhook admission 503/resumption or polling readiness after webhook deletion, and process-local wizard/queue limitations. A post-ready webhook failure must clear transport readiness until polling starts. A lost update cannot be repaired by discovery and there is no replay queue; do not start another poller for testing.
- For **management → booking**, only after the separate booking mutation and legacy/restore gates have been met, review `BOOKING_SERVICE_KEY` and the exact v2 facility binding, set `DISCOVERY_MODE=registry`, keep the registry bootstrap, and set `SPORTS_BOOKING_SERVICE_URL=` empty. Verify booking contract/capabilities and precisely one eligible instance before *any authorized mutation*. Status and credentialed reconciliation use the original immutable operation key and scope. A missing registry/booking instance, unknown provider result, failed status read or changed facility never permits keyless fallback, a new account/key, or automatic cancellation replay. Explicit duplicate-risk authorization is a separate owner action, not part of a discovery drill.
- **Compose staging constraint:** production Compose currently passes the *same* `.env` `DISCOVERY_MODE` value to management, Telegram and web. A global `.env` flip would switch **all three** at once. For a per-class switch/rollback use an owner-reviewed, per-service Compose environment override or separately deployed projects; verify the **rendered** config for each service before starting it, with the other classes still static and their static URLs intact. Do not assume the shared `.env` alone can stage classes independently. Re-evaluate targets, leases, ready counts, alerting and rollback conditions after **each** caller class; do not switch all callers at once. Observe the scheduler's local-time booking window and process-local Telegram conversations separately: no discovery availability metric proves a missed window or in-memory queue can be replayed. If any stage fails, stop that stage rather than weakening a selector or entering credentials on a different facility.

## 4. Routing rollback and incidents

- Roll back **invocation**, not state: pause booking/cancellation mutations before changing the management caller, let known in-flight operations drain and inspect unknown ones by the **same** key. For the affected caller class, stop its old process, restore `DISCOVERY_MODE=static` and its reviewed, compatible static `MANAGEMENT_SERVICE_URL` or `SPORTS_BOOKING_SERVICE_URL`; then start only one replacement. If shadow monitoring is still wanted, keep `DISCOVERY_URL` for registration. Never interpret an empty/unavailable registry as an empty booking ledger. A registry/DB outage is not a signal to bypass descriptor or facility checks.
- Static booking rollback is only to a **keyed v2** client and matching v2 booking binary. Preserve management registry tables/catalog/leases, `management_booking_*` intents/keys/lineage, booking's `booking_*` ledger/migrations, `BOOKING_IDENTITY_KEY`, active claims, imports, tombstones and unresolved evidence. Do not drop either migration stream, invent a no-effect outcome, replay an external operation under a new key or delete a booked court just to unblock a deployment. If the old binary is keyless/v1, keep mutations disabled and retain compatible v2 status/reconciliation access; follow [booking rollback](booking-reliability-runbook.md#8-rollback) before any resumption.
- Stop-before-start singleton replacement also applies during network migration and crash recovery. Drain closes admission first and deregisters only after the listener/execution budget; forced termination may leave a lease until expiry, and a fresh registry does not erase durable booking state. Separate management/DB outages from booking-only and monitoring-only failures; booking can remain directly usable when management is stopped, but registry-only clients cannot freshly resolve without it. Preserve possible duplicate liability until verified provider evidence resolves it.
- Only propose retiring overlapping `scripts/healthcheck.sh` cron alerts **after** the owner has tested external Grafana notifications and resolved messages, static management loss, last-instance expiry, Prometheus/path/whole-host loss, and authorized/unauthorized query reachability. Keep an independent monitoring path for Prometheus failure; do not silence both signals merely because a synthetic PromQL test passed.
